What is UX ?
• If UI referred to how the interface looks, then UX refers to
how the application feels
• UX is about how the user feels when interacting with the
application
• Is the interaction pleasant ?
• Is the interaction logical ?
• Does the application requires to much effort to operate for its
purpose ?
• Do the data flow logically between the interfaces ?
• Do the data required really required ?
<!-- p3 -->
What is UX ?
• Is the interaction pleasant ?
• This means that I don’t dislike the interface
• I can see myself using the application
• Is using the application feels organic and natural, or is it a chore
like cleaning your room? If it is the latter, you need to re-evaluate
the design
• Is the interaction logical ?
• This means that I can understand the general way the application
operates easily
• This allows the user to better understand the interface and how to
interact with it
<!-- p4 -->
What is UX ?
• Does the application requires to much effort to operate for its
purpose ?
• Is the number of steps and operations needed to achieve the goal too much ?
• Can I reduce the number of steps needed to achieve the goal ?
• Do the data flow logically between the interfaces ?
• This one is extremely important.
• Generally, interfaces in an application needs to share data and information
among them.
• This creates a flow of data from one interface to the other, notably in wizard
interfaces (like the ones used to install applications)
• Does this flow relate to the goal of the application ?
• Does it help it or hinder it ?
• Does it allow the application to function easily ?
• The data flow must be fluent, logical and easy to understand.
<!-- p5 -->
What is UX ?
• Do the data required really required ?
• In other word, the user should enter the required data only to
achieve the goal.
• We must not require data that is not needed, this will distract the
user, and will harm a fluent data flow.
• If a lot of data is required, a good idea is to split the data into
groups, then use sequential interfaces to enter each group alone
(know as a wizard).
• Another good idea is to split the data between required and
optional groups, where the latter can be skipped or hidden under
“more details” button or something.

Number of Clicks
• Number of clicks is a term referring to the number of items
(buttons, menus, interfaces, ...etc) you are required to click
in order to reach a certain action.
• You can classify the actions in your interface to categories,
where the most important actions require 0 click to reach,
while less important requires more.
• Take the save button in MS Office, it is placed in the top
left(for English)/right (for Arabic) corner of the interface,
above the ribbon bar, why?
• This action is very important. Thus far, it must be 0 clicks
away from the user to activate it.
<!-- p8 -->
Number of Clicks
• Huawei took a great deal of pride on how they redesigned
Android settings application interface, where no setting is
farther than 3 clicks from the main interface.
• This means no matter the option you want, it is at most 3
interfaces away from you.
<!-- p9 -->
Number of Clicks
• The most obvious location to really utilize the number of clicks is the settings
interface of your application.
• In general, the average user will change few settings, power user will change
a lot of settings.
• Average is more common than power. Therefore, a good practice is to design
the main settings interface with the common user in mind, and create an
advanced setting interface for the power user.
• Usually, the settings a power user would like to change, can cause instability
in the application, or sometimes a full on crash.
• A good practice is to either remove these settings completely and hard code
them, or burry them in the settings behind a lot of clicks so the average user
won’t easily gain access to them.
• You can also remove them from the interface, but keep them in the settings
file to manually change them (the Linux way)
<!-- p10 -->
Number of Clicks
• This goes not just for setting, but for all other interfaces.
• But it is not a must, if there is a need follow this method.

Foolproof Design
• When ever you want to create an interface remember 2
platinum rules:
1. The user of your application is the dumbest person in the world.
2. The user of your application is the smartest person in the world.
• What does that mean ?
• It means the interface must robust enough to handle accidental
and intentional wrong input or interaction from the user.
• To understand this will look at few examples:
• Date picker
• Disable when incomplete
<!-- p12 -->
Foolproof Design
• Date picker
• When you want the user to input date why choose a date picker field, if can
use simpler text field?
• Can you guarantee the user will correctly format the date ?
• Required: DD/MM/YYYY
• Provided: MM/DD/YYYY
• Can you guarantee the user will insert correct date ?
• 31/2/2021 ?!
• Can you guarantee the user will actually insert date and perform for example
SQL injection ?
• By using date picker, a component ensures the input of correct date in the
intended format, and allows the user to easily select the proper date through
the use of a calendar, you ensure the previous problems never occur. Not to
mention it will make your application easier to use.
<!-- p13 -->
Foolproof Design
• Disable when incomplete
• A personal favorite of mine.
• It means the “save” or “next” button gets disabled until all the
essential data is inserted by the user.
• This actually prevents missing fields problem, specially if the
application has a database backend with not null fields.
• However, a simple disable is not enough, we need to provide a
visual clew to the user about what’s missing:
• Add an asterisk * to the label of the required field to indicate not null
• Surround the input field with red borders until the correct data is inserted
• Add an error message displayed around the field to indicate incorrect or
missing input, hiding it when correct data is inserted.
<!-- p14 -->
Foolproof Design
• Disable when incomplete
• This will prevent the dumbest user form accidentally bricking the
application.
• This will prevent the smartest user from intentionally bricking the
application.

Impaired Design
• Many people have disabilities that require certain design
changes in order to make the experience better
• We classify disabilities into 3 categories:
• Visual Sensory Disabilities
• Auditory Disabilities
• Motor Function Disabilities
<!-- p16 -->
Impaired Design
• Visual Sensory Disabilities:
• This includes people who have difficulties seeing the interface, can
be divided into 3 sub categories:
• Blind
• Color Blind
• Poor Vision
<!-- p17 -->
Impaired Design
• Visual Sensory Disabilities:
• Blind
• People who can’t see the interface at all.
• For these people we rely on auditory feed back by utilizing text to speech
• This available in all major operating system, as it provides an application
specifically designed to speak the entire screen.
• Even more, some web browsers implement there own version of this to
speak an entire web page.
• This operates by utilizing mouse cursor, despite being blind when moving
the cursor the system detects the text underneath it and speaks it

Impaired Design
• Visual Sensory Disabilities:
• Color Blind
• These are people who cannot see the normal color spectrum the average
human sees, and there are several types of color blindness:
• Red-Green:
1. Protanopia: can’t see red
2. Protanomaly: can see
some shades of red
3. Deuteranopia: can’t see
green
4. Deuteranomaly: can see
some shades of green
• Blue-Yellow
1. Tritanopia: can’t see blue
2. Tritanomaly: can see some
shades of blue
• Monochromacy:
Zero color vision only shades of gray

Impaired Design
• Visual Sensory Disabilities:
• Color Blind
• Developing the interface to provide a good experience to all these type is
kind of an expensive undertake
• The best approach is to actually create a high contrast color ratio, while color
blind people can’t see a color, they can see its lightness.
• JetBrains IDEs provide an option to enable color schemes for 2 types of color
blindness Protanopia, Deuteranopia
<!-- p20 -->
Impaired Design
• Visual Sensory Disabilities:
• Poor Vision
• This by far is the simplest visual sensory disability, just make the text bigger
and clearer.
• However, the UI elements must not break when increasing font size
• Some application, especially on Android, hard code the font size, and as a
result they don’t respond to system wide change in font size.
• The developer might do that to insure consistent experience, but as more of
the generation that started using computer is getting older, their eyes are
getting weaker and this needs to be addressed.

Impaired Design
• Auditory Disabilities:
• This refers to people who can’t or have weak hearing
• In this regard a flashy popup is a good choice
• Or if you are working in mobile land, an aggressive use of the
phone haptic engine (the shaky thingy) is a good idea to attract
attention
• Various OSes relies on audio notification to get the attention of the
user
• But in case they have a bad hearing, we need to rely on shaking
and flashy notifications

Impaired Design
• Motor Function Disabilities
• Speech commands:
• In the old days, controlling your computer through voice alone was difficult,
now it is a common feature, after the massive advance in A.I., networking
infrastructure and speed, many tools perform speech recognition in the
cloud after hearing the command.
• Like Amazon Alexa, Google Assistant (Now switched to Bard), Apple Siri,
Microsoft Cortana (RIP).
• The idea is simple, if you can’t use the mouse or touch screen to do an
action, tell the computer to do it using your voice.
• This would actually require the developers to either create their own speech
recognition engine, a very mean feat.
• Or use an existing SDK to access an already provided engine.

Impaired Design
• Motor Function Disabilities

• For example, on Android, you can actually utilize Google Assistant in your

Impaired Design
• Motor Function Disabilities
• Specialized hardware
• Sometimes, people suffer a medical condition (e.g. brain stroke) that
prevents them from speaking or using their motor function.
• In this case, we need to create specialized hardware to act on behalf of the
person.
• Many research centers goes to create some sort of neural implant to places
in or on the head (long before Elon Musk’s Neural Link) to act as a new limb
for the person
• This allows the computer to read thoughts and convert them to actions.
• In this case the general software interface must simplified and the items
enlarged to allow for greater surface to interact with, for these devices are
not 100% accurate.
